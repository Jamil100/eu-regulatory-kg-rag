# ADR 0015: Benchmark accuracy on replayed passages, cost and latency on a live pass; publish six columns and break refusal out

- **Status:** Accepted
- **Date:** 2026-08-15
- **Deciders:** Jamil (project owner)
- **Context phase:** Phase 5 — three-way benchmark and publication

## Context

The README opens with a benchmark table whose every cell is `–`. Filling it means
running three systems — vector-only, vector + Rerank 3.5, full hybrid — over the
eval set and reporting per-stratum accuracy, p95 latency and cost per query.

Four things had to be decided before any money was spent, because each one can be
chosen after seeing the results in a way that flatters them. They are recorded
here, and enforced by `tests/test_run_benchmark.py`, so that the protocol is
falsifiable rather than reconstructed.

Everything published in this repo before Phase 5 measures **gold-chunk
retention** — did the right passage reach the model. ADR-0013, ADR-0014 and
`docs/metrics/answer-path.md` all say in writing that retention is not accuracy
and that Phase 5's judge is what closes the gap. This ADR is about how that
closing is measured.

## Decision 1 — Two passes, because one cannot serve both columns

**Accuracy is measured on replayed passages. Latency and cost are measured on a
separate live pass.**

`answer_path.replayed_passages(field=...)` reads committed orderings out of
`eval/rerank-eval.jsonl` and fetches text from Postgres. All three systems then
see byte-identical passages, so a difference between them is a difference in the
system rather than a different vector draw. That is what makes the accuracy
columns comparable — and it is the same trade `retrieve_detailed(vector=...)` and
`answer(passages=...)` already exist to make.

It also makes the vector half cost `$0.00` and skips the embed round trip
entirely, so latency and cost from that pass would be fiction. Hence the second
pass. Rows carry `mode` and `scoreboard()` keeps them apart;
`test_accuracy_comes_from_replayed_rows_only` and
`test_cost_and_latency_come_from_live_rows_only` pin the separation.

This mirrors the split `src/api/ask_eval.py` already draws between the pipeline
artifact and the interface artifact, for the same reason: one artifact cannot
honestly answer two questions with different denominators.

### The live vector baseline needs its own retrieval, and this is not an optimisation

`answer()` hardwires retrieve→rerank in its vector branch
(`answer_path.py:294-312`). A live sweep that simply called it for the vector-only
system would **pay for and use a reranker that system is defined as not having**,
making vector-only identical to vector+rerank in exactly the two columns the live
pass exists to produce. The symptom would have been a suspiciously equal pair of
numbers in the published table and nothing else.

So the live vector arm calls `retrieve_detailed` itself and injects the
un-reranked top-5. It still pays the embed round trip — that is the honest cost of
a vector-only system — and does not pay the rerank.
`test_the_live_vector_baseline_does_not_go_through_the_reranker` asserts this
structurally, because the failure is silent.

## Decision 2 — Six headline columns, refusal broken out beneath

The README table keeps its six accuracy columns (single-hop, two-hop, three-hop,
cross-regulation, aggregation, refusal) and adds, immediately beneath it, a
three-column sub-table splitting refusal into `out-of-scope`, `unanswerable` and
`hard-negative`.

Roadmap §5.3 defines **eight** strata, and both it and `docs/metrics/eval-set.md`
argue that averaging the three refusal modes "hides which behaviour actually
failed" — they have three different correct outputs, and two of them are exact
opposites (`out-of-scope` and `unanswerable` must cite *nothing*; `hard-negative`
must cite). `plan-phase-3-router-and-query-path.md:778-780` flagged the
contradiction between the table and the roadmap as a Phase 5 blocker.

An eleven-column headline table wraps badly on GitHub and roadmap §6 Phase 5.4 is
explicit that "nobody scrolls; the table and video decide". The sub-table keeps
the scannable headline without averaging away a distinction the repo has argued
for twice. `test_the_markdown_table_breaks_refusal_out_instead_of_averaging_it`
pins it.

**Cells are `n/N`, never bare percentages.** At five rows a refusal stratum has no
meaningful percentage, and rounding one to "80%" hides the denominator that makes
it readable.

**The table is generated by `markdown_table()`, never transcribed.** Step 5's
recurrence was a figure computed once by hand and copied into the repo, so a test
ended up comparing a constant to itself (`failure-notes.md`, "Verified once by
hand, never encoded").

## Decision 3 — Per-system p95, no per-stratum p95

At 100 rows a system has enough observations for a tail figure. A stratum has 5 to
20, and a p95 over 5 observations is the maximum wearing a percentile's name.

`ask_eval.py:20-28` made the same refusal at 23 rows, and
`test_no_per_route_p95_is_published` made it structural there. The equivalent here
is `test_no_per_stratum_p95_is_published`, so a later step cannot add one without
deleting a test that explains why not.

Percentiles are nearest-rank, not interpolated: an interpolated p95 invents a
value no request ever took, and the column reports what was observed.

Rows with `attempts > 1` are excluded from the percentile — a call that retried
spent most of its wall clock asleep in tenacity backoff, and averaging that in
produces a number about the API key rather than about the system.

## Decision 4 — One imposed denominator, and two buckets that are not accuracy

**`common`.** Each system drops its own errored and `MAX_TOKENS` rows and they are
not the same rows, so three per-system accuracies are three different populations
and "28 of 51" against "28 of 47" reads as a tie between things never measured on
the same set. `common` is the set of rows *every* system scored. It is smaller and
weaker than the per-system number and it is the one that is comparable. Both are
printed, labelled. This is the same defect `answer_path.scoreboard()` solved for
budget arms and that `template_selector._report` once shipped as "Ceiling 10 of 9".

**`expected_fail`.** Rows carrying a recorded reason — currently `3h-002`, where
the extractor emits `PERMITS` on the Art. 6(3) derogation that the row declares as
`EXEMPT_FROM` (ADR-0007) — go in their own bucket. Counting them as passes
silences the canary; counting them as system failures blames the retrieval stack
for an extraction gap.

**Ungraded rows.** A judge failure is a fact about the grader, so an ungraded row
is reported as ungraded and never scored `wrong` against the system.

**Retention is reported beside accuracy, not replaced by it.** Every pre-Phase-5
number in this repo is retention, and a system whose retention rises while its
accuracy does not has found the passages and failed to use them — which is a
finding, and only visible if both are on the page.

## Consequences

- The benchmark cannot be run until `rerank-eval.jsonl` is re-swept over the
  100-row eval set; the committed one holds 23 rows. Same for the router,
  selector and answer-path artifacts, whose published denominators are stale.
- Two passes cost roughly twice one pass. Estimated ~$2 for three systems plus
  ~$0.30 for judging, against a one-time ingestion cost of ~$24 — the marginal
  honesty is cheap relative to the build.
- `--refresh` takes one system per invocation. ~100 chat calls against a
  rate-limited key is long enough that a single sweep can exhaust the tenacity
  budget, and an arm that dies halfway must not take the other two with it.
  `attempts` is recorded per row so a rate-limited row is visible in the artifact
  rather than inferred from a bad score.
- `scoreboard()` is pure — no database, no key, no network — so `--eval`
  reproduces the published table with the containers down. Asserted structurally
  by `test_scoreboard_touches_no_database_and_no_network`.

## Alternatives considered

**One live pass for everything.** Simpler and cheaper, and it is what the roadmap
implies. Rejected because the three systems would then see three different vector
draws, so a per-stratum difference could not be attributed to the system rather
than to retrieval variance — which is the entire claim the table exists to make.

**Eight headline columns.** Most faithful to roadmap §5.3. Rejected on
readability; the sub-table preserves the information at the cost of one extra
line of scrolling.

**Averaging the three refusal strata into one column.** Simplest. Rejected
because the repo has twice argued in writing that this hides which behaviour
failed, and adopting it here would have required retracting that argument rather
than merely departing from it.

**Cohen's kappa for judge agreement.** Rejected in favour of raw agreement:
kappa needs a marginal distribution to correct against, and over a 20-row
stratified holdout with four labels those marginals are themselves noise. The
disagreement rows are named individually instead, because *which* labels moved
matters more than how many — a 90% that disagrees on both refusal rows is a worse
grader than a 90% that disagrees on two single-hop rows.
